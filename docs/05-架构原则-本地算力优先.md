# 架构原则：本地算力优先 + 云端轻接入

> 记录一套在"个人 / 小团队 + AI Agent"场景下反复验证过的部署判断，避免每次都从"先买台云服务器"开始想问题。
> 本文是**原则与判断边界**，不是某个具体项目的设计。

---

## 一、一句话原则

> **不要默认把算力租在云端；把云端看成可替换的网络入口，把本地高性能机器看成主要计算资源。只有本地确实不适合承担的能力，才交给云端。**

更准确的表述是：**本地计算优先、云端轻量接入、按需混合部署**。

---

## 二、为什么"云端为中心"在 AI Agent 场景里不划算

| 维度 | 传统 Web 项目 | AI Agent 项目 |
|------|--------------|---------------|
| 主要压力 | 并发、数据库、带宽、可用性 | **模型推理、多 Agent 并行、浏览器自动化、文档解析、向量检索、多步工具调用** |
| 资源特征 | 平稳、可预测 | 突发、差异极大（有的任务几乎不吃 CPU，有的吃满 GPU） |
| 云端计费逻辑 | 按"全天候公共服务"设计，合理 | 为偶发/间歇的重计算**长期租同级实例 = 浪费** |

**一个容易被忽略的事实**：Agent 不一定消耗很多本地算力。如果它主要负责调用云端大模型 API、组织工具调用、维护任务状态，算力其实在模型服务商那一侧。**只有当你需要本地推理、高并发 Agent、复杂沙箱或大量浏览器任务时，本地硬件才会成为瓶颈**——显存需求还随模型大小、量化方式、上下文长度剧烈变化。

所以值得本地化的**不是所有东西**，而是：**计算成本高、需要长期运行、隐私敏感，或用现有硬件更划算**的任务。

---

## 三、三层划分（而不是简单的"本地 vs 云端"）

```
第一层  用户入口        手机 App · 浏览器 · 外部 API · Webhook
          │
第二层  云端轻接入      DNS · HTTPS 终止 · 反向代理 · 安全策略 · 必要的公网路由
          │
第三层  本地计算与调度   本地入口 → 任务队列 → 调度器 → 多个 Agent Worker
                       （本地模型 / 数据与检索 / 沙箱 / 浏览器自动化）
```

配套原则：**把任务调度与任务执行解耦**。任务进队列后，由调度器按任务类型、资源需求、优先级、节点状态决定执行位置；将来换机器、加显卡、加第二台主机，不需要重构整个应用。

---

## 四、三个功能分别该放在哪

| 功能 | 更适合放在 | 原因 |
|------|-----------|------|
| 公网流量入口与边缘安全 | **云端 / 边缘网络** | 用户必须先能从互联网访问到入口 |
| Agent 任务队列与 Worker 调度 | **本地优先** | 能直接掌握本机 CPU/GPU/显存与任务状态 |
| 多台计算机器之间的负载均衡 | **本地调度器或独立调度服务** | 要按真实算力、队列长度、资源占用分配工作 |

**这三个概念不要混为一谈**：

- **隧道**（如 Cloudflare Tunnel）：本机发起出站连接，把私有服务安全接入公网，不用开放入站端口；**它不负责决定哪个任务该跑在哪张 GPU 上**。
- **反向代理**（如 Nginx）：终止 TLS、分发路径、缓冲/流式控制。
- **负载均衡**：在多个执行者之间分配工作，依据应是真实资源，而不是网络层轮询。

---

## 五、云服务器什么时候仍然值得花钱

不要一刀切说"云服务器鸡肋"，用边界判断：

| 场景 | 建议 | 理由 |
|------|------|------|
| 个人工具、私有 Agent、独立开发项目 | **本地优先** | 用户有限、机器本来就要开机、任务可排队、短时不可用可接受 |
| 提供给外部用户的 AI 服务 | **混合部署** | 本地算力 + 云端稳定入口/认证/任务接收/必要持久化；**必须为"本地 Worker 离线、带宽不足、并发峰值"设计降级** |
| 持续高并发、全球用户、强可用性 | **云端计算** | 要求全天候可访问、快速扩容、地理就近；纯本地的可用性维护成本可能更高 |

**算总账**：硬件折旧 + 电费 + 网络 + 备份 + 维护时间 + 可用性损失，再对比云端实际省下的钱——而不是只比 VPS 月租。

---

## 六、这套原则不会自动解决的问题（必须自己处理）

把计算放回本地**不会**让这些问题消失：

1. **单点故障**：一台本地主机断电 / 系统崩溃 / 断网 → 服务就没了。云端再配十层代理也救不回来。
2. **任务语义**：超时、重试、**幂等性**、结果持久化、节点断线后的恢复。
3. **入口体验**：本地离线时，入口应给出**明确的"服务离线"提示**，而不是让用户面对白屏或超时。
4. **暴露面**：公网暴露后的访问控制（认证、限流、审计）——入口变轻了，不等于可以不管安全。

### 本机实测到的两条具体约束（写下来避免重犯）

- **守护进程与自启要单独设计**：本机服务若以"前台进程"方式启动，**重启电脑后不会自动回来**；真正稳的做法是把它做成 Windows 服务或计划任务（本机入口层的隧道就是服务形式，实测重启后能自动重连）。
- **宿主机休眠 = 全站不可用**：本机当服务器的第一件事是把睡眠/休眠关掉，否则会出现"隧道好好的、服务却每天随机掉线"的假故障。

---

## 七、与"网页转 App"的关系

按这套原则，手机 App 的定位就清楚了：

> **App 只负责访问与交互；云端负责安全接入；本地调度器负责把请求交给相应的业务服务或 Agent。**

也就是说，App 里**不应该内置业务重逻辑**——它就是一个带图标、带名称、能装的口子。所以"网页套壳"（Capacitor 容器 + 远程 URL）在这套架构里不是偷懒，而是**正确的分层**：前端迭代不需要重新发版，重计算全部留在本地。

代价也要认：远程 URL 模式下 **App 强依赖网络与本机在线**，本机停了 App 就是错误页——这是该模式的固有属性，正式发布前要重新评估（见 `docs/03` 的两种打包模式）。
