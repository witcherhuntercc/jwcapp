# 移动端适配与容器能力（为什么"App 里像网页"）

> **什么时候看这篇**：手机上的 App 出现"内容顶到状态栏""右滑直接退出到桌面""整个像网页全屏"这类现象时。
> **一句话结论**：**这不是"网页套壳"的架构缺陷，而是容器只做了"显示网页"、没做"移动端运行时"**——补插件 + 少量前端适配即可。
> **配套工具**：[../scripts/check-mobile-readiness.ps1](../scripts/check-mobile-readiness.ps1)（出包前自检，能直接列出缺口）

---

## 一、判断标准：什么才算架构缺陷

| 类型 | 例子 | 判定 |
|------|------|------|
| **能力边界问题** | 需求在 WebView 里根本做不到：常驻后台服务、深度系统集成、高性能图形/动画 | ❌ 这才是选型缺陷 |
| **配置 / 适配问题** | 状态栏、返回键、键盘遮挡、安全区、点击高亮 | ✅ 有官方插件或标准 CSS 解法，属"成本"不属"缺陷" |

> 经验：**先问"官方有没有插件/标准做法"**。有 → 是配置问题；没有且绕不过 → 才需要重新选型。

---

## 二、为什么 uni-app（HBuilder X）没这些问题

| 三件事 | uni-app / 5+ runtime | Capacitor（裸装状态） |
|--------|---------------------|---------------------|
| 状态栏 | runtime 用**原生导航栏**占位，页面天然从状态栏下方开始 | 只给裸 WebView，**不管** insets → 内容顶上去 |
| 返回手势 | runtime 接管 BACK → 映射到**原生页面栈**；无历史时提示"再按一次退出" | 默认**无历史就直接退出应用**，不映射前端路由 |
| 安全区 / 键盘 | runtime 内置处理 | **按需装插件**（status-bar / keyboard / haptics…） |

**定位差异，不是能力差异**：uni-app 是"电池已装"，Capacitor 是"最小内核 + 按需装电池"。
所以看到"网页味"，先查"电池装了没"，而不是怀疑路线。

**另一个容易误判的点**：Android 15+（`targetSdk ≥ 35`）会**强制 edge-to-edge**——这是**系统行为，原生 App 同样要自己处理 insets**。跟 Capacitor 无关。

## 三、修复对照表（哪一侧解决）

| 现象 | 容器侧能否单独解决 | 做法 |
|------|:---:|------|
| 内容顶到状态栏 | ✅ 能（前端一行不改） | 装 `@capacitor/status-bar` → `StatusBar.setOverlaysWebView({ overlay: false })`（WebView 落在状态栏下方） |
| 右滑/返回键直接退出 | ✅ 能 | 装 `@capacitor/app` → 监听 `backButton`：有可回退历史就回退，否则弹"再按一次退出"再 `App.exitApp()` |
| 高度/滚动异常（页面比可视区高） | ⚠️ 部分 | 前端把 `100vh` 换成 `100dvh`（WebView 里 `100vh` 含状态栏高度） |
| 刘海/手势条遮挡局部元素 | ⚠️ 需前端 | 根容器统一 `padding: env(safe-area-inset-*)` |
| 键盘顶起内容异常 | ✅ 能 | 装 `@capacitor/keyboard` 按需处理 |
| 启动白屏 | ✅ 能 | 装 `@capacitor/splash-screen` |

**关键结论**：主要症状（状态栏、返回键）**都能在容器侧解决，不必改业务前端**；只有"高度算错/局部遮挡"这类才需要前端配合。

## 四、标准做法（新项目接进来就该做）

### 容器侧

```powershell
npm i @capacitor/app @capacitor/status-bar
npx cap sync android
```

```ts
// 应用初始化处（示意）
import { App } from '@capacitor/app'
import { StatusBar } from '@capacitor/status-bar'

await StatusBar.setOverlaysWebView({ overlay: false })   // 内容从状态栏下方开始

App.addListener('backButton', ({ canGoBack }) => {
  // canGoBack 由 WebView 历史决定；SPA 建议结合前端路由判断
  if (canGoBack || 前端路由可回退) { history.back() /* 或 router.back() */ }
  else { 弹"再按一次退出"确认框 → 确认后 App.exitApp() }
})
```

### 前端侧（`index.html` + 全局样式）

1. `viewport` 加 `viewport-fit=cover`（缺了 `env(safe-area-inset-*)` 全部失效）；
2. 根容器统一吃安全区：`padding-top: env(safe-area-inset-top)`、底部同理（手势条）；
3. `100vh` → `100dvh`；
4. 顺手做掉"网页味"：`-webkit-tap-highlight-color: transparent`、`overscroll-behavior: none`（禁下拉回弹）、按需禁长按选中。

## 五、出包前自检（别靠记忆）

```powershell
.\scripts\check-mobile-readiness.ps1 -ProjectDir <Capacitor工程> -WebSource <前端源码目录>
```

会逐项列出：插件是否齐、打包模式、`targetSdk` 是否触发强制 edge-to-edge、`viewport-fit=cover`、安全区变量使用量、`100vh` 用量、点击高亮。
**结论里出现 FAIL 就先补，别出包**。

## 六、选这条路要付的三笔长期账（不阻塞，但要知道）

1. **双端适配债**：同一份前端要同时服务浏览器和 App，每次改版都要在真机回归一遍。
   （uni-app 原生渲染页面没这负担，代价是把前端重写到它的组件体系）
2. **WebView 的交互天花板**：复杂动画性能、原生手感（下拉刷新、边缘滑动跟手度）永远差原生一档。
3. **远程 URL 模式的依赖**：App 打开依赖网络 + 服务在线；服务一停就是错误页，正式发布前需重新评估。

> 这三条是**选 WebView 套壳要付的钱**，不是"这条路走不通"。要彻底消除，只能换成原生渲染（重写前端）或混合（关键页面 nvue/原生组件）。
